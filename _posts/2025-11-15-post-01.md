## Introduction

As a developer working on healthcare analytics applications, I needed a way to develop and test code against data structures that mirror the U.S. Department of Veterans Affairs (VA) Corporate Data Warehouse (CDW). The challenge? The production CDW is a massive, secure, enterprise system running across VA's infrastructure with strict access controls and containing protected health information (PHI) for millions of veterans.

The solution? Build a complete simulation environment on a macOS laptop using Docker, Microsoft SQL Server 2019, and Python-based synthetic data generation tools. This blog post documents how I created a fully functional development environment that replicates the CDW's data model, schemas, and ETL patterns—all with synthetic data and running locally on a laptop.

This guide will take you from a brand new macOS laptop to a fully functioning development environment, complete with:

- A containerized SQL Server 2019 database
- CDW-compliant database schemas and tables
- Synthetic patient data generation tools
- ETL pipelines for data processing
- A complete data mart for analytics

Whether you're a VA contractor, healthcare IT professional, or developer interested in healthcare data engineering, this guide will show you how to create a safe, isolated development environment for building applications that integrate with VA systems.

## Background: The VA Corporate Data Warehouse

### What is the VA CDW?

The VA Corporate Data Warehouse (CDW) is a Microsoft SQL Server-based enterprise data warehouse that consolidates clinical, administrative, and operational data from over 140 Veterans Health Administration (VHA) medical facilities across the United States. Each facility runs an instance of the Veterans Health Information Systems and Technology Architecture (VistA), a comprehensive electronic health record (EHR) system.

### CDW Architecture and Purpose

The CDW serves as the authoritative source for VA healthcare data, aggregating information from disparate VistA systems into a unified data model. It supports:

- **Clinical Analytics**: Patient outcomes analysis, quality measures, and population health management
- **Operational Reporting**: Resource utilization, appointment scheduling, and facility performance metrics
- **Research**: De-identified datasets for medical research and epidemiological studies
- **Administrative Functions**: Claims processing, eligibility determination, and program management

### CDW Data Model

The CDW uses a dimensional data model organized into subject-area schemas:

- **SPatient**: Patient demographics, enrollment, eligibility, and veteran status
- **Inpat**: Inpatient admissions, transfers, discharges, and census data
- **Outpat**: Outpatient visits, appointments, and clinic encounters
- **SStaff**: Healthcare providers, clinicians, and administrative staff
- **Dim**: Dimension tables for locations, facilities, time periods, and reference data

Data is identified across the VA enterprise using several key identifiers:

- **PatientSID**: Surrogate ID for patient records in the CDW
- **PatientICN**: Integration Control Number, the enterprise-wide patient identifier
- **PatientIEN**: VistA-specific Internal Entry Number
- **Sta3n**: Three-digit station number identifying the VA medical facility
- **SSN**: Social Security Number (encrypted/scrubbed in most environments)

### The Challenge for Developers

Developing applications that integrate with the CDW requires:

1. **Access to a CDW-like environment** with realistic data structures
2. **Test data** that mirrors production patterns without containing PHI
3. **ETL tools** to extract, transform, and load data following VA patterns
4. **A safe, isolated environment** for development and testing

Building this environment locally solves these challenges without requiring access to production or test VA systems.

### Component Details

**med-data: Source System Simulation**
- **Purpose**: Simulates the VA CDW source database
- **Technology**: Microsoft SQL Server 2019 (Docker container)
- **Database**: `CDWWork`
- **Schemas**: `Dim`, `Inpat`, `SPatient`, `SStaff`
- **Content**: SQL scripts for schema creation, table definitions, and synthetic data insertion
- **Python Tools**: Data generation utilities for creating realistic test datasets

**med-etl: ETL Pipeline**
- **Purpose**: Extracts data from CDWWork, transforms it, and loads it into a data mart
- **Technology**: Python 3.13+ with pandas, pyodbc, and pyarrow
- **Database**: `Extract` (SQL Server) for processed data
- **Features**:
  - Interactive CLI menu system
  - Support for multiple extract types (ADM, CLI, DEM, LAB, RAD)
  - ASCII fixed-width format generation (for legacy system compatibility)
  - Parquet file generation (for modern analytics)
  - Comprehensive logging and error handling

**med-view: Analytics Web Application**
- **Purpose**: Provides web-based interface for data visualization and reporting
- **Technology**: PHP 8.4+, MariaDB, Apache httpd
- **Features**: Dashboard, filtering, FHIR/HL7 integration (not covered in this guide)

**med-output: External Output Directory**
- **Purpose**: Stores generated files outside the source code repository
- **Location**: `~/swdev/med/med-output/`
- **Contents**:
  - `_extract/`: ETL-generated extract files (ASCII format)
  - `_log/`: Application log files from all subsystems

### Data Flow Architecture

```
1. SCHEMA CREATION
   ├─▶ Run SQL scripts to create CDWWork database
   ├─▶ Create schemas (Dim, Inpat, SPatient, SStaff)
   └─▶ Create tables with VA CDW structure

2. DATA GENERATION
   ├─▶ Run SQL scripts to insert synthetic data
   └─▶ Python utilities generate additional test data

3. ETL PROCESSING
   ├─▶ Extract: Query CDWWork database by extract type
   ├─▶ Transform: Apply business rules and formatting
   └─▶ Load: Write to Extract database and ASCII files

4. ANALYTICS (med-view)
   ├─▶ Query Extract database for reporting
   └─▶ Display dashboards and visualizations
```

## Installation Guide

This section provides step-by-step instructions to set up your development environment from scratch. Each command is explained with expected output so you can verify success at each step.

### Step 1: Install Homebrew

Homebrew is the package manager for macOS that simplifies software installation.

**1.1: Check if Homebrew is already installed**

```bash
brew --version
```

If you see a version number (e.g., `Homebrew 4.2.0`), skip to Step 2. Otherwise, continue.

**1.2: Install Homebrew**

```bash
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
```

Follow the prompts to complete installation. The installer will:
- Download and install Homebrew
- Install Xcode Command Line Tools if needed
- Add Homebrew to your PATH

**1.3: Add Homebrew to your PATH (if prompted)**

If the installer shows instructions like this, follow them:

```bash
echo 'eval "$(/opt/homebrew/bin/brew shellenv)"' >> ~/.zprofile
eval "$(/opt/homebrew/bin/brew shellenv)"
```

**1.4: Verify installation**

```bash
brew --version
```

Expected output: `Homebrew 4.2.0` (or later)

### Step 2: Install Docker Desktop

Docker Desktop provides the container platform for running SQL Server 2019 on macOS.

**2.1: Install Docker Desktop via Homebrew**

- Wait for Docker to start (Docker icon in menu bar will show "Docker Desktop is running")

CONTAINER ID   IMAGE     COMMAND   CREATED   STATUS    PORTS     NAMES

The second command should show an empty list (no containers running yet).

**2.4: Configure Docker resources (optional but recommended)**

- Click Docker icon in menu bar → Settings
- Go to Resources → Advanced
- Allocate at least:

### Step 6: Pull and Start SQL Server 2019 Container

Now we'll download the SQL Server 2019 container image and create a running container.

**6.1: Pull the SQL Server 2019 image**

```bash
docker pull mcr.microsoft.com/mssql/server:2019-latest
```

This downloads approximately 1.5 GB. It may take several minutes depending on your internet connection.

**6.2: Create and start the SQL Server container**

```bash
docker run -d \
  --name sqlserver2019 \
  -e 'ACCEPT_EULA=Y' \
  -e 'SA_PASSWORD=MyS3cur3P@ssw0rd' \
  -p 1433:1433 \
  mcr.microsoft.com/mssql/server:2019-latest
```

**Command explanation:**
- `-d`: Run in detached mode (background)
- `--name sqlserver2019`: Name the container for easy reference
- `-e 'ACCEPT_EULA=Y'`: Accept the SQL Server End User License Agreement
- `-e 'SA_PASSWORD=MyS3cur3P@ssw0rd'`: Set the system administrator (sa) password
- `-p 1433:1433`: Map container port 1433 to host port 1433
- Image name: `mcr.microsoft.com/mssql/server:2019-latest`

**Security Note**: In a production environment, use a stronger password and secure credential management. For local development with synthetic data, this password is acceptable.

**6.3: Verify the container is running**

```bash
docker ps
```

Expected output:
```
CONTAINER ID   IMAGE                                       STATUS          PORTS                    NAMES
abc123def456   mcr.microsoft.com/mssql/server:2019-latest  Up 30 seconds   0.0.0.0:1433->1433/tcp   sqlserver2019
```

**6.4: Test SQL Server connectivity**

```bash
sqlcmd -S 127.0.0.1,1433 -U sa -P 'MyS3cur3P@ssw0rd' -Q "SELECT @@VERSION"
```

Expected output should show SQL Server version information:
```
Microsoft SQL Server 2019 (RTM-CU18) (KB5017593) - 15.0.4261.1 (X64)
...
```

If you see this output, SQL Server is running correctly!

**6.5: Configure Docker to start container on boot (optional)**

```bash
docker update --restart unless-stopped sqlserver2019
```

This ensures SQL Server starts automatically when Docker Desktop launches.

## Troubleshooting

### SQL Server Connection Issues

**Problem**: `sqlcmd` cannot connect to SQL Server

**Solution 1**: Verify container is running

```bash
docker ps
```

If not running:

```bash
docker start sqlserver2019
```

**Solution 2**: Check Docker logs

```bash
docker logs sqlserver2019
```

Look for errors related to startup or licensing.

**Solution 3**: Restart the container

```bash
docker restart sqlserver2019
# Wait 30 seconds for SQL Server to start
sleep 30
```

### Python ODBC Driver Issues

**Problem**: `pyodbc` cannot find ODBC driver

**Error message**: `[01000] [unixODBC][Driver Manager]Can't open lib 'ODBC Driver 18 for SQL Server'`

**Solution**: Verify ODBC driver installation

```bash
odbcinst -q -d
```

You should see:
```
[ODBC Driver 18 for SQL Server]
```

If not, reinstall:

```bash
brew reinstall msodbcsql18 unixodbc
```

### Docker Desktop Performance

**Problem**: Docker is slow or containers crash

**Solution**: Increase Docker resource allocation

1. Click Docker icon in menu bar → Settings
2. Resources → Advanced
3. Increase CPU and Memory allocations
4. Apply & Restart

**Recommended settings:**
- CPUs: 4
- Memory: 8 GB
- Swap: 1 GB
- Disk image size: 40 GB

### Disk Space Issues

**Problem**: Docker reports "no space left on device"

**Solution**: Clean up Docker resources

```bash
docker system prune -a
```

This removes unused containers, images, and volumes.

### Virtual Environment Issues

**Problem**: Python packages not found even after `pip install`

**Solution**: Ensure virtual environment is activated

```bash
cd ~/swdev/med/med-insight/med-etl
source venv/bin/activate
```

Your prompt should show `(venv)`.

**Solution 2**: Recreate virtual environment

```bash
deactivate  # If already in venv
rm -rf venv
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

### Extract Files Not Generating

**Problem**: ETL runs but no files appear in `_extract/` directory

**Solution**: Check .env file paths

```bash
cd ~/swdev/med/med-insight/med-etl
cat .env | grep EXTRACT
```

Verify `ASCII_EXTRACT_FOLDER` path exists:

```bash
ls -ld ~/swdev/med/med-output/_extract
```

Create if missing:

```bash
mkdir -p ~/swdev/med/med-output/_extract
```

### Permission Issues

**Problem**: "Permission denied" errors when creating files

**Solution**: Check directory ownership

```bash
ls -ld ~/swdev/med/med-output
```

Fix ownership if needed:

```bash
sudo chown -R $(whoami) ~/swdev/med/med-output
```

2. **Synthetic Data Enables Innovation**: By using synthetic data that matches production structures, we can develop and test freely without security and privacy concerns.

3. **Infrastructure as Code**: All database schemas, tables, and ETL logic are defined in SQL scripts and Python code, making the environment reproducible and version-controlled.

4. **Separation of Concerns**: The monorepo structure (med-data, med-etl, med-view) cleanly separates data sources, processing logic, and presentation layers.
